# Design: add-d-agr-cred-load

## Context

DDS-слой банковского хранилища (Greenplum, схема `s_grnplm_vd_t_bvd_db_dmslcl`). Таблица `d_agr_cred` — реестр кредитных договоров; наполняется тремя потоками через `UNION ALL`: ЭКС (из `d_agr_cred_tmp` и сервисных представлений `didsd_010`), ВДО (`didsd_029`), core/COA (`d_coa_cred_core` + `v_coa`). Загрузка существует как единственный монолитный `INSERT` (349 строк). В этом изменении SQL фиксируется как есть — в `sql/d_agr_cred_load.sql` — и обрастает спекой, регламентом и проверками.

## Goals / Non-Goals

**Goals:**

- Зафиксировать контракт загрузки в спеке `credit-agreements` (поведение, правила выбора атрибутов, гарантии).
- Оформленный регламент: полная перезагрузка, порядок шагов, повторный запуск без дублей.
- DQ-проверки после каждой загрузки: уникальность ключа, NOT NULL ключевых атрибутов, сверка количеств по потокам, контрольные примеры правил.

**Non-Goals:**

- Переписывание или оптимизация SQL (рефакторинг — отдельные изменения при необходимости).
- Изменение состава колонок и типов (`UNION ALL`-выравнивание — как есть).
- Партиционирование и производительность (на текущих объёмах не является проблемой).

## Decisions

1. **Сохранить монолитный `INSERT` как реализацию.** SDD фиксирует поведение, а не форму SQL. Вынесение в файл + спека дают основу для точечных изменений (например, «вынести вычисление `crncy_id` в отдельный шаг» — отдельное изменение).
2. **Очистка целевой таблицы — часть регламента, до `INSERT`.** В тексте запроса очистки нет; в регламенте фиксируем порядок (очистка/секционная замена) и добавляем pre-check свежести `d_agr_cred_tmp`. Где именно сейчас выполняется очистка — открытый вопрос к владельцу (см. ниже).
3. **DQ-проверки — отдельные запросы после загрузки** (уникальность `agr_cred_id`; NOT NULL; сверка `COUNT(*)` по потокам с источниками; контрольные примеры). Это исполнимая часть гарантий из спеки.
4. **Недетерминированный предикат `('now'::text)::date` в `d_agr_cred_cust`** — фиксируем как известное отклонение: результат зависит от даты запуска. Кандидат на параметризацию датой отчёта в следующем изменении; текущий контракт не ломает.
5. **Подзапрос валют (`row_number() ... ORDER BY NULL::text` + условие `max = min`)** трактуем как защиту от неоднозначной валюты счёта: если у счёта не одно значение валюты, атрибут не заполняется и срабатывает фолбэк. Оставляем как есть; упрощение — кандидат на будущее.

## Risks / Trade-offs

- [Пересечение `agr_cred_id` между потоками] → DQ-проверка уникальности; провал блокирует приёмку загрузки.
- [Изменения в представлениях `didsd_010` / `didsd_029` меняют результат] → сверки количеств и контрольные примеры в задачах; периодический прогон DQ.
- [Полная перезагрузка большой таблицы] → на текущих объёмах приемлемо; при росте — секционная замена (отдельное изменение).

## Migration Plan

Изменение brownfield: текущий SQL фиксируется как baseline (git-тег `01-baseline`), затем добавляются спека/регламент/DQ (теги `02-change1-proposal` → `03-change1-archived`). Откат — состояние baseline: загрузка продолжает работать и без спек.

## Open Questions

- Где выполняется очистка `d_agr_cred` (TRUNCATE / загрузка в новую секцию) — уточнить у владельца таблицы и зафиксировать в регламенте.
- Нужна ли история версий (SCD) или таблица всегда полная — влияет на формулировку требования идемпотентности.
